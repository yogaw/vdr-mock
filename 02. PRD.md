## 1. Overview

### 1.1 Summary

A Secure Virtual Data Room (VDR) where an **Admin** curates collections of confidential
documents into *data rooms* and grants time-boxed access to **Viewers**. Viewers browse and
read documents inside a secure in-app viewer stamped with a forensic watermark. Download is a
privilege, not a default: when disabled, there is **no technical path** to obtain the file —
only authorized, server-validated viewing.

### 1.2 Problem

Sharing sensitive documents (due diligence, legal, financial) via email or generic cloud
drives provides no access control after the fact, no view tracking, and no leak deterrence.

### 1.3 Value Propositions

1. **Controlled Access** — admins decide who can enter which data room and touch which documents.
2. **Secure View-Only Documents** — documents can be restricted to in-app viewing with no download path.
3. **Dynamic Forensic Watermarking** — every view is stamped with viewer identity and timestamp.

---

## 2. Goals & Non-Goals

### 2.1 Goals

- Ship an MVP VDR with authentication, two roles, data rooms, folders, and documents.
- Enforce all document access **server-side**, on every request.
- Provide view-only documents with dynamic watermark and zero client-exposed storage URLs.
- Give admins an audit trail of logins, views, downloads, and admin actions.
- Provide a single admin dashboard for rooms, users, documents, and activity.

### 2.2 Non-Goals (explicitly out of scope for MVP)

Per `OBJECTIVES.md`, this scope is deliberately tight. The following are **not** in the MVP
unless explicitly requested later:

- DRM or copy-protection beyond watermarking (screenshots cannot be prevented)
- Full-text search / OCR
- Granular workspace hierarchies (multi-level orgs, teams, projects above rooms)
- Bulk import, drag-drop of entire folder trees
- Real-time co-editing, annotations, comments, Q&A modules
- Advanced email infrastructure (digests, templated campaigns) beyond a simple invitation
- Custom roles / RBAC editor (two fixed roles only)
- Mobile native apps (responsive web only)
- Data room templating, cloning, branding customization
- Watermark on downloaded files (MVP watermarks the *viewer* only)

## 4. Users & Roles

### 4.1 Personas

- **Admin (VDR Operator)** — manages rooms, documents, users, permissions, and reviews activity. Trusted user with full control within assigned rooms.
- **Viewer (External Party)** — invited guest (e.g., investor, auditor, counsel). Can only see rooms they were granted, and only act within the permissions configured.

### 4.2 Role Permission Matrix

| Capability | Admin | Viewer |
|---|:---:|:---:|
| Create / edit / delete data room | ✅ | ❌ |
| Create / rename / move / delete folders | ✅ | ❌ |
| Upload / replace / delete documents | ✅ | ❌ |
| Manage users (create, invite, deactivate, remove) | ✅ | ❌ |
| Grant / revoke / expire room access | ✅ | ❌ |
| Configure download & watermark settings | ✅ | ❌ |
| View audit & activity logs | ✅ | ❌ |
| View assigned data rooms | ✅ (all) | ✅ (assigned only) |
| Browse permitted folders | ✅ | ✅ (permitted only) |
| Open permitted documents | ✅ | ✅ (permitted only) |
| Download document | ✅ | ⚠️ only when `download_allowed = true` |
| See activity logs of own actions | — | ❌ (MVP: no self-service log) |

Two roles only. No custom roles in MVP.

## 5. Functional Requirements

Priority key: **P0** = must have for MVP launch · **P1** = should have, planned for MVP cycle ·
**P2** = stretch / fast-follow.

### 5.1 Authentication — `FR-AUTH`

| ID | Requirement | Priority |
|---|---|:---:|
| FR-AUTH-1 | Users must authenticate (email + password) before accessing any data room content. Unauthenticated requests to any app route redirect to login. | P0 |
| FR-AUTH-2 | Password reset via time-limited, single-use reset token delivered out-of-band (email link, or copyable link in admin UI if email is not configured). | P0 |
| FR-AUTH-3 | Optional MFA: admin can require TOTP-based MFA per user ("sensitive users"). Login then requires a valid TOTP code. (No SMS in MVP.) | P2 |
| FR-AUTH-4 | Sessions expire automatically after inactivity (default 30 min, configurable). Expired sessions redirect to login. | P0 |
| FR-AUTH-5 | Passwords stored using a modern adaptive hash (argon2id or bcrypt, cost-appropriate). Plaintext passwords are never stored or logged. | P0 |

### 5.2 User & Access Management — `FR-ACC`

| ID | Requirement | Priority |
|:---:|---|:---:|
| FR-ACC-1 | Admin can create/invite users (email + display name), deactivate, and permanently remove users. | P0 |
| FR-ACC-2 | Invitation mechanism: system generates a single-use, time-limited invitation link; the invitee sets their own password via that link. (Simple email send if configured; otherwise the link is shown to the admin to share over a secure channel.) | P0 |
| FR-ACC-3 | Admin can grant a user access to specific data rooms (room-level access is the baseline). | P0 |
| FR-ACC-4 | Admin can set an **expiry date** on a user's room access; expired access is denied automatically on the next request. | P0 |
| FR-ACC-5 | Admin can **revoke** access immediately; revocation takes effect on the viewer's next request (no waiting for token expiry beyond the short-lived content token window, ≤ 60 s). | P0 |
| FR-ACC-6 | Optional folder-level permission: within an accessible room, admin can restrict a user to specific folders. | P1 |
| FR-ACC-7 | Optional document-level permission: admin can restrict access to individual documents. | P2 |
| FR-ACC-8 | Deactivated/removed users cannot log in; their sessions are invalidated. | P0 |

### 5.3 Data Room Management — `FR-ROOM`

| ID | Requirement | Priority |
|:---:|---|:---:|
| FR-ROOM-1 | Admin can create a named data room (name, optional description). | P0 |
| FR-ROOM-2 | Admin can archive/delete a data room; deletion removes or renders inaccessible all contained documents. | P0 |
| FR-ROOM-3 | Room-level security defaults: `download_allowed` (default **off**) and `watermark_enabled` (default **on**) set at creation, editable later. | P0 |
| FR-ROOM-4 | Admin can create, rename, move, and delete folders within a room. | P0 |
| FR-ROOM-5 | Folder structure is limited to a practical nesting depth (recommend max 5 levels); no limits UI beyond that in MVP. | P1 |

### 5.4 Document Management — `FR-DOC`

| ID | Requirement | Priority |
|:---:|---|:---:|
| FR-DOC-1 | Admin can upload documents: **PDF** required; DOCX/XLSX/PPTX and common office formats accepted. | P0 |
| FR-DOC-2 | Upload enforces a max file size (default 100 MB, configurable) and validates the declared type against the file's actual content signature (magic bytes), not just the extension. | P0 |
| FR-DOC-3 | Admin can replace/update a document; the new file keeps the same room/folder location and document ID. Replacement is versioned (`version` increments). | P0 |
| FR-DOC-4 | Admin can delete a document (soft-delete; storage object removed or quarantined). | P0 |
| FR-DOC-5 | Admin can rename a document and move it between folders. | P1 |
| FR-DOC-6 | Per-document security settings override room defaults (see §7). | P0 |

### 5.5 Secure Viewer — `FR-VIEW`

| ID | Requirement | Priority |
|:---:|---|:---:|
| FR-VIEW-1 | Browser-based in-app viewer; PDFs render inside the app (e.g., PDF.js-style rendering). No external viewer redirect. | P0 |
| FR-VIEW-2 | Office documents (DOCX/XLSX/PPTX) are converted server-side to PDF for preview **where supported**; unsupported files show a graceful "preview not available" state. | P1 |
| FR-VIEW-3 | The original storage URL/key must never be exposed to the client (not in HTML, JS bundles, network payloads, or error messages). | P0 |
| FR-VIEW-4 | Document content is delivered only through the backend content endpoint after the full authorization chain passes (§10). Supports HTTP Range requests for progressive PDF loading. | P0 |
| FR-VIEW-5 | Viewer disables right-click/download context menu affordances and prints-a-page shortcuts where feasible (best-effort deterrence; server-side rules remain the real control). | P1 |

### 5.6 Download Control — `FR-DL`

| ID | Requirement | Priority |
|:---:|---|:---:|
| FR-DL-1 | Download is configurable per room and per document (document overrides room). | P0 |
| FR-DL-2 | When `download_allowed = false`: no download action is rendered **and** the download API refuses the request server-side (403). | P0 |
| FR-DL-3 | When `download_allowed = true`: viewer can download; every download is recorded in the log with user, document, timestamp, IP. | P0 |
| FR-DL-4 | The backend re-validates identity → room access → document permission on **every** download/content request. No cached authorization decisions across settings changes. | P0 |

### 5.7 Dynamic Watermark — `FR-WM`

| ID | Requirement | Priority |
|:---:|---|:---:|
| FR-WM-1 | When a document is viewed and watermarking is enabled, a dynamic watermark overlay appears automatically over the rendered pages. | P0 |
| FR-WM-2 | Watermark content includes: viewer **name** and/or **email**, **current date/time**, and optionally the **data room name** — each individually toggleable (§7). | P0 |
| FR-WM-3 | Watermark **repeats** across the entire viewed page/document (tiled/diagonal pattern), not a single corner stamp. | P0 |
| FR-WM-4 | Watermark is configurable per room and per document (document overrides room); can be disabled. | P0 |
| FR-WM-5 | Watermark is rendered for every page the viewer navigates to, and reflects the actual viewer identity of the current session (a shared screen/link shows the current user's mark). | P0 |
| FR-WM-6 | (Explicitly non-goal for MVP: watermarking downloaded files; preventing screenshots.) | — |

### 5.8 Activity Tracking & Audit — `FR-LOG`

| ID | Requirement | Priority |
|:---:|---|:---:|
| FR-LOG-1 | Record login events (success and failure) with timestamp and IP. | P0 |
| FR-LOG-2 | Record every document view: user, document, room, timestamp, IP, user agent. | P0 |
| FR-LOG-3 | Record every allowed download: user, document, timestamp, IP. | P0 |
| FR-LOG-4 | Admin audit log records: permission grants/changes/revocations, room creation/edit/deletion, uploads, replacements, deletions, user lifecycle events, security-settings changes. | P0 |
| FR-LOG-5 | Logs are append-only in the UI (no edit/delete affordance for admins). | P1 |
| FR-LOG-6 | Logs are filterable by user, room, document, event type, and date range; paginated. | P1 |

### 5.9 Admin Dashboard — `FR-DASH`

| ID | Requirement | Priority |
|:---:|---|:---:|
| FR-DASH-1 | Data room list: all rooms with document counts and active user counts. | P0 |
| FR-DASH-2 | User access summary: which users have access to each room, incl. expiry dates. | P0 |
| FR-DASH-3 | Recent activity feed: latest document views/downloads. | P1 |
| FR-DASH-4 | Document management: browse/manage documents and their security settings from one screen. | P0 |
| FR-DASH-5 | Audit log viewer (per FR-LOG). | P1 |

### 5.10 Notifications — `FR-INV`

| ID | Requirement | Priority |
|:---:|---|:---:|
| FR-INV-1 | Invitation delivery per FR-ACC-2 (email if configured; copyable secure link otherwise). | P0 |
| FR-INV-2 | No other notification infrastructure in MVP (no digests, no alerts on view events). | — |

## 6. User Flows

### 6.1 Admin Flow

```
Login
→ Create Data Room (set room defaults: download=off, watermark=on)
→ Create folders
→ Upload documents
→ Configure document security:
   - Viewer access
   - Allow download: Yes / No
   - Watermark: On / Off (+ watermark content fields)
→ Invite user (email + name)
→ Assign user to Data Room (optionally set expiry date)
→ User receives invitation
→ Admin monitors activity (dashboard / audit log)
```

### 6.2 Viewer Flow

```
Receive invitation → set password via invite link
→ Login (optional MFA if required)
→ Open assigned Data Room
→ Browse folders (permitted only)
→ Select document
→ Open document in secure viewer
   → authorization chain passes server-side
   → dynamic watermark appears (identity + timestamp, repeated)
```

### 6.3 Download Branching (Viewer)

```
IF download_allowed = false
   → no download action available in UI
   → direct API attempt returns 403 (server-side refusal)

IF download_allowed = true
   → user may download
   → download recorded in audit log (user, document, timestamp, IP)
```

### 6.4 Access Expiry / Revocation

```
IF room access has expired (expires_at < now)
   → room and its documents invisible & inaccessible on next request

IF admin revokes access
   → same effect, effective immediately (≤ short-lived token window)
```

## 7. Document Security Settings

Each document carries a settings object. Room defaults seed new documents; per-document
values override room defaults.

```
Document Security Settings

Access
[✓] Viewer can access            → doc.access_enabled (default: true)

Download
[ ] Allow download               → doc.download_allowed (default: room default; rooms default OFF)

Watermark
[✓] Enable watermark             → doc.watermark_enabled (default: room default; rooms default ON)

Watermark content:
[✓] User email                   → doc.wm_include_email
[✓] User name                    → doc.wm_include_name
[✓] Date & time                  → doc.wm_include_timestamp
[✓] Data room name               → doc.wm_include_room_name
```

Rules:

- At least one watermark content field must be selected when watermark is enabled (UI enforces; fallback default = email + timestamp).
- Effective settings = document override if set, else room default.
- Settings changes apply to subsequent requests; no long-lived credential may encode them.

## 8. Conceptual Data Model

Entities (implementation-agnostic; fields indicative, not exhaustive):

```
User            id, email (unique), name, password_hash, role (admin|viewer),
                status (active|disabled), mfa_secret (nullable), created_at

Invitation      id, email, token_hash, expires_at, created_by, accepted_at

DataRoom        id, name, description, status,
                default_download_allowed, watermark_enabled (+ wm_* content flags),
                created_by, created_at, deleted_at

Folder          id, room_id, parent_folder_id (nullable), name

Document        id, room_id, folder_id, name, original_filename, mime, size_bytes,
                storage_key, version, access_enabled,
                download_allowed (nullable override), watermark_enabled (nullable override),
                wm_* (nullable overrides), uploaded_by, created_at, deleted_at

AccessGrant     id, user_id, room_id, granted_by, expires_at (nullable), revoked_at (nullable)

FolderAccess    id, user_id, folder_id            (P1)
DocumentAccess  id, user_id, document_id          (P2)

ActivityEvent   id, user_id, event_type (login|login_failed|view|download|admin_action),
                room_id?, document_id?, ip, user_agent, detail (JSON), created_at
```

Notes:

- `ActivityEvent` doubles as the viewer activity log and the admin audit trail (`event_type = admin_action`, `detail` carries the specifics).
- Soft deletes (`deleted_at`) support audit integrity.
- Access checks always evaluate: user active AND grant exists AND `revoked_at IS NULL` AND (`expires_at IS NULL OR expires_at > now()`).

## 9. Non-Functional Requirements — `NFR`

### 9.1 Security (non-negotiable)

| ID | Requirement |
|:---:|---|
| NFR-SEC-1 | **Private storage** — file objects live in access-controlled storage (private bucket or non-public local volume). No public read policy, ever. |
| NFR-SEC-2 | **Server-proxied content delivery** — document bytes are streamed by the backend after authorization. Short-lived (≤ 60 s), single-purpose content tokens may be issued only *after* the authorization chain passes. Storage keys/URLs never reach the client. |
| NFR-SEC-3 | **Server-side authorization on every request** — identity → room access → document permission is re-evaluated per request. Frontend hiding is never the control. |
| NFR-SEC-4 | **Encryption in transit** — TLS/HTTPS everywhere, including the content endpoint; HTTP redirected or refused. |
| NFR-SEC-5 | **Encryption at rest** — encrypted storage for files (e.g., SSE on object storage) and encrypted database volumes. |
| NFR-SEC-6 | **Session timeout** — idle sessions expire (FR-AUTH-4). |
| NFR-SEC-7 | **Least disclosure** — 404 (not 403-with-details) for documents outside a viewer's visibility, to avoid existence leaks; errors never leak storage paths. |
| NFR-SEC-8 | **Secrets** — storage credentials, signing secrets, and DB credentials via environment/secret manager, never in code or client bundles. |
| NFR-SEC-9 | **Transport of originals** — downloads, when allowed, are streamed by the backend with `Content-Disposition: attachment`; no redirect to a storage URL. |

### 9.2 The Authorization Chain (contract)

Every request for document content or metadata **must** pass, server-side, in order:

```
User requests document (view or download)
        ↓
1. Backend checks identity (valid session / token)          → else 401
        ↓
2. Backend checks data room access (grant, not revoked,
   not expired, folder/doc-level rules if enabled)           → else 404
        ↓
3. Backend checks document permission (access_enabled,
   download_allowed for downloads)                           → else 403
        ↓
4. Viewer receives authorized content (streamed bytes) + view/download is logged
```

Rules that follow:

- The original storage URL must never be exposed to the client.
- Document content is served only through short-lived, server-authorized access.
- Authorization is evaluated server-side on every request — never via frontend hiding alone.

### 9.3 Performance & Scalability

| ID | Requirement |
|:---:|---|
| NFR-PERF-1 | Room listing and folder browsing respond < 500 ms (p95) at MVP scale (≤ 50 rooms, ≤ 5k documents, ≤ 200 users). |
| NFR-PERF-2 | First page of a 5 MB PDF renders in the viewer < 3 s on broadband (Range-request streaming). |
| NFR-PERF-3 | Upload of a 100 MB file completes without worker timeout; processing (type validation, office→PDF conversion) is asynchronous with a "processing" state where needed. |

### 9.4 Reliability & Operations

| ID | Requirement |
|:---:|---|
| NFR-OPS-1 | Audit/activity events are written on the request path (synchronously or durable-queued); a logging failure fails closed for downloads, alerts for views. |
| NFR-OPS-2 | Application logs (system logs) never contain document bytes, passwords, or tokens in plaintext. |
| NFR-OPS-3 | Backups: database backed up daily; storage versioning or backup per hosting capability. |

## 10. API Surface (indicative)

For planning purposes; exact shapes are an engineering decision. All endpoints require
authentication unless noted. All document endpoints enforce the §9.2 chain.

```
Auth
POST   /api/auth/login                    (public)
POST   /api/auth/logout
POST   /api/auth/password/reset-request  (public)
POST   /api/auth/password/reset          (public, token)
POST   /api/auth/accept-invitation       (public, invite token + new password)

Rooms & structure (admin; viewers read-only where noted)
GET    /api/rooms                        (viewer: only granted rooms)
POST   /api/rooms
GET    /api/rooms/:id
PATCH  /api/rooms/:id                    (incl. security defaults)
DELETE /api/rooms/:id
POST   /api/rooms/:id/folders
PATCH  /api/folders/:id
DELETE /api/folders/:id

Documents (admin writes; viewers read/list)
GET    /api/rooms/:id/documents          (folder filter; viewer: permitted only)
POST   /api/rooms/:id/documents          (multipart upload)
PATCH  /api/documents/:id                (rename, move, security settings)
POST   /api/documents/:id/replace        (new version, same location)
DELETE /api/documents/:id

Secure content & download
GET    /api/documents/:id/content        (VIEW — streamed, Range-supported,
                                          watermark rules applied client-side
                                          per effective settings)
GET    /api/documents/:id/download       (DOWNLOAD — 403 unless allowed;
                                          Content-Disposition: attachment)

Users, access, invitations (admin)
GET    /api/users
POST   /api/users/invite
PATCH  /api/users/:id                    (deactivate, role, MFA flag)
DELETE /api/users/:id
POST   /api/rooms/:id/access             (grant; optional expires_at)
DELETE /api/rooms/:id/access/:userId     (revoke)

Activity (admin)
GET    /api/activity                     (filters: user, room, document, type, date)
```

Design note: `content` and `download` are **separate endpoints** so the server can apply
different rules (download requires `download_allowed = true` and logs a `download` event;
`content` always logs a `view` event). Short-lived view tokens, if used, are minted only
after the chain passes and are bound to user + document + purpose + ≤ 60 s TTL.

## 11. UX Requirements (summary)

1. **Viewer UI** — clean document viewer: page navigation, zoom, page count. Watermark overlay tiles across every visible page. No download button when downloads are disabled.
2. **Admin UI** — dashboard-first: rooms table → room detail (folders/documents tree) → document drawer with security settings (§7 form). Users & access page with expiry dates visible at a glance.
3. **Viewer home** — shows only assigned rooms; empty state explains "your administrator will grant access" and shows access expiry where relevant.
4. **Responsive** — usable on tablet; desktop is the primary target.
5. **Processing states** — uploads and office→PDF conversions show progress/processing status; errors surface clearly.

## 12. Acceptance Criteria (MVP Definition of Done)

### 12.1 Core journeys

- **AC-1** Admin can create a room, folders, and upload a PDF; the PDF appears in the viewer's room.
- **AC-2** Admin can invite a user, grant room access (with expiry), and the invitee can log in via the invitation link and see exactly that room.
- **AC-3** Viewer opens a PDF; it renders in-app; a repeated watermark with their name/email and current timestamp overlays every page.
- **AC-4** With download disabled, the viewer sees no download affordance **and** a crafted `GET /api/documents/:id/download` returns 403.
- **AC-5** With download enabled, the viewer can download; the event appears in the activity log with user/document/time/IP.
- **AC-6** After the admin sets an expiry in the past (or revokes), the viewer's next request is denied and the room disappears from their list.
- **AC-7** Deactivated user cannot log in; existing sessions are rejected.
- **AC-8** Admin dashboard shows rooms, per-room user access summary, recent views/downloads, and the audit log with permission changes.
- **AC-9** Password reset flow works end-to-end via time-limited token.

### 12.2 Security test checklist (release gate)

- [ ] Unauthenticated `GET /api/documents/:id/content` → 401.
- [ ] Authenticated viewer without grant → 404 (no existence leak).
- [ ] Viewer with grant, download disabled, hitting download endpoint → 403.
- [ ] Room settings changed to disable download → next download request refused (no stale authorization).
- [ ] No storage URL/key appears in any HTML/JS/network payload for a document request.
- [ ] Direct object-storage URL (if guessed/constructed) is not publicly readable.
- [ ] Expired grant → denied within the documented window (≤ 60 s worst case).
- [ ] Watermark contains the *current* session's user identity, and timestamp reflects view time.
- [ ] Content endpoint honors Range requests (PDF pagination) without bypassing auth.
- [ ] TLS enforced; plaintext HTTP does not serve content.
- [ ] Audit log contains entries for every view and download performed in testing.

## 14. Assumptions & Open Questions

### Assumptions

1. Single-tenant deployment; one admin org. (Multi-tenancy is out of scope.)
2. Web app (SPA or SSR) served over HTTPS; responsive, desktop-first.
3. Object storage (S3-compatible or equivalent) or a private server volume for files — both acceptable provided §9.1 holds.
4. Email delivery is optional; where absent, invitation/reset links are surfaced to the admin to deliver via a secure channel of their choice.
5. Watermark is an overlay in the viewer (deterrence/forensics), not cryptographic protection.

### Open Questions

| # | Question | Default if unresolved |
|:---:|---|---|
| 1 | Email provider available for invitations/resets? | Copyable-link fallback (Assumption 4) |
| 2 | Office→PDF conversion: which engine (LibreOffice headless vs. hosted API)? | Server-side LibreOffice-style conversion behind a feature flag; graceful "no preview" fallback |
| 3 | Should MFA ship in MVP or fast-follow? | Fast-follow (P2, FR-AUTH-3) |
| 4 | Folder-level permissions in first release? | Yes for P1 cycle (FR-ACC-6); document-level P2 |
| 5 | Specific hosting target / compliance regime (SOC2, ISO, regional data residency)? | Generic encrypted cloud per NFR-SEC-5; no compliance claim in MVP |
| 6 | Max upload size and accepted type whitelist? | 100 MB default; PDF + DOCX/XLSX/PPTX (+ images optional) |

## 15. Glossary

| Term | Meaning |
|---|---|
| **Data Room** | A named collection of folders/documents with its own access list and security defaults. |
| **Grant** | A user's access to a room, optionally time-boxed (`expires_at`) or revoked. |
| **Effective settings** | Document-level override if set, otherwise room default (download/watermark). |
| **Authorization chain** | identity → room access → document permission, evaluated server-side per request. |
| **Forensic watermark** | Repeated viewer overlay identifying who is viewing and when — deters and traces leaks. |
| **View-only** | `download_allowed = false`: in-app viewing only; no server-side download path exists. |
