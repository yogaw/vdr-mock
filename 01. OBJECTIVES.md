# Secure Virtual Data Room (VDR) — MVP Objectives

This document defines the objectives, feature scope, user flows, permission model, and
non-negotiable security behavior for the MVP build of the Secure Virtual Data Room.

**Product scope:** Secure Virtual Data Room MVP

**Primary value propositions:**

1. **Controlled Access** — admins decide who can enter which data room and touch which documents.
2. **Secure View-Only Documents** — documents can be restricted to in-app viewing with no download path.
3. **Dynamic Forensic Watermarking** — every view is stamped with viewer identity and timestamp.

This scope is deliberately tight. Do **not** expand it into a full enterprise VDR build
(no DRM, no OCR search, no granular workspace hierarchies, no email infra beyond a simple
invitation mechanism) unless explicitly requested.

## 1. Core VDR Feature List

### Authentication

| Feature | Description |
|---|---|
| User Login | Users must authenticate before accessing any data room |
| Password Reset | Allow users to securely reset their password |
| Optional MFA | Configurable additional verification for sensitive users |

### Access Management

| Feature | Description |
|---|---|
| User Management | Admin can create, invite, deactivate, and remove users |
| Role Management | Minimum roles: **Admin** and **Viewer** |
| Data Room Access | Admin can define which user can access which data room |
| Folder Access | Optional permission at folder level |
| Document Access | Optional permission at individual document level |
| Access Expiration | Admin can set an expiry date for a user's access |
| Revoke Access | Admin can immediately revoke access |

### Data Room

| Feature | Description |
|---|---|
| Create Data Room | Admin can create a named data room/project |
| Folder Management | Create, rename, move, and delete folders |
| Document Upload | Upload PDF and common office documents |
| Document Replace | Replace/update a document while preserving its location |
| Document Delete | Admin can remove documents |

### Document Viewer

| Feature | Description |
|---|---|
| Browser-based Viewer | User can open and view documents directly inside the application |
| PDF Preview | PDF should render inside the secure viewer |
| Office Document Preview | DOCX/XLSX/PPTX can be converted or previewed where supported |
| No Direct File URL | Original storage URL must not be exposed to the user |

### Download Control

| Feature | Description |
|---|---|
| Configurable Download | Admin can enable or disable download per room/document |
| View-only Mode | When download is disabled, document can only be opened inside the viewer |
| Download Authorization | Backend must validate permissions before generating any downloadable file |

### Watermark

| Feature | Description |
|---|---|
| Dynamic Watermark | Watermark automatically appears when the document is viewed |
| User Identification | Watermark includes viewer name and/or email |
| Timestamp | Include current viewing date/time |
| Data Room Name | Optional room/project identifier |
| Repeated Watermark | Watermark should repeat across the document rather than appear only once |
| Configurable Watermark | Admin can enable/disable watermark per room/document |

### Activity Tracking

| Feature | Description |
|---|---|
| Login Activity | Record when users enter the system |
| Document View Log | Record which user opened which document and when |
| Download Log | Record all allowed downloads |
| Admin Audit Log | Record permission changes, uploads, deletions, and access revocations |

### Admin Dashboard

| Feature | Description |
|---|---|
| Data Room List | See all active data rooms |
| User Access Summary | See which users have access to each room |
| Recent Activity | Show recent document views/downloads |
| Document Management | Manage documents and security settings from one screen |

### Security

| Feature | Description |
|---|---|
| Private Storage | Files must not be publicly accessible |
| Signed/Temporary Access | Use short-lived server-authorized access to retrieve documents |
| Encryption in Transit | HTTPS/TLS required |
| Encryption at Rest | Files and database should use encrypted cloud storage |
| Server-side Authorization | Permissions cannot rely only on frontend hiding |
| Session Timeout | Automatically expire inactive sessions |

## 2. User Flows

### Admin Flow

```
Login
→ Create Data Room
→ Create folders
→ Upload documents
→ Configure document:
   - Viewer access
   - Download allowed: Yes / No
   - Watermark: On / Off
→ Invite user
→ Assign user to Data Room
→ User receives invitation
→ Admin can see activity
```

### Viewer Flow

```
Receive invitation
→ Create account / Login
→ Open assigned Data Room
→ Browse folders
→ Select document
→ Open document in secure viewer
→ Dynamic watermark appears
```

### Download Branching (Viewer)

```
IF download_allowed = false
→ no download action available

IF download_allowed = true
→ user may download
→ download recorded in audit log
```

## 3. Permission Model

Keep the first version simple — two roles only.

**ADMIN**

- Create/edit/delete data room
- Upload/delete documents
- Manage users
- Configure access
- Configure download
- Configure watermark
- View audit logs

**VIEWER**

- View assigned data room
- Browse permitted folders
- Open permitted documents
- Download only when allowed

```
Watermark
[✓] Enable watermark

Watermark content:
[✓] User email
[✓] User name
[✓] Date & time
[✓] Data room name
```

## 5. Non-Negotiable Behavior — Server-Side Enforcement

> When download is disabled, do **not** simply remove the Download button while leaving a
> public PDF URL accessible. Someone could inspect browser network traffic and retrieve the
> document directly.

The application **must** enforce the following chain on every document request:

```
User requests document
        ↓
Backend checks identity
        ↓
Backend checks Data Room access
        ↓
Backend checks document permission
        ↓
Secure viewer receives authorized content
```

Rules that follow from this:

- The original storage URL must never be exposed to the client.
- Document content is served only through short-lived, server-authorized access.
- Authorization is evaluated server-side on every request — never via frontend hiding alone.
