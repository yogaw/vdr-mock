## 1. Purpose

The current phase develops a **UI mock** of the Secure VDR MVP: plain HTML/CSS/JS pages that
demonstrate every screen and flow defined in the PRD, using simulated data and simulated
security behavior. The mock validates layout, flows, and interaction design before any real
backend work begins.

## 2. Hard Constraints (mock phase)

1. **Plain stack only**: HTML + CSS + JavaScript. No frameworks, no bundlers, no build step,
   no package.json, no CDN dependencies.
2. **Runs by double-click**: every page opens directly in a browser via its `index.html`
   (`file://` works; no server required).
3. **One folder per page**: all code for a page lives in `mock/<page-name>/`.
4. **Kebab-case** folder and file names, lowercase.
5. System fonts only. No external images — use emoji/SVG/CSS shapes for icons and avatars.

> ⚠️ **Security disclaimer** — a mock runs entirely in the browser, so *none* of the PRD's
> server-side enforcement (§9.2 authorization chain, NFR-SEC-*) exists here. Mocked
> "restrictions" (hidden download buttons, fake 403 alerts) are **UI simulations for design
> validation only**. They must never be read as the enforcement model, and mock code is not
> a starting point for production security logic.

## 3. Folder Structure

```
mock/
├── _shared/
│   ├── base.css          # shared tokens: colors, fonts, buttons, tables, layout
│   ├── mock-data.js      # seed data: users, rooms, folders, documents, grants, events
│   └── mock-helpers.js   # session (localStorage), navigation guards, logging helpers
│
├── login/
│   ├── index.html
│   ├── style.css         # page-specific styles only
│   └── script.js         # page behavior only
│
├── rooms/                # ...same 3-file pattern per page
├── viewer/
└── ...
```

Rules:

- Each page folder contains exactly `index.html`, `style.css`, `script.js`.
- Pages link shared assets relatively: `<link href="../_shared/base.css">`,
  `<script src="../_shared/mock-data.js"></script>`.
- `base.css` holds the design system (tokens + shared components). Page `style.css` only adds
  page-specific rules. If a rule appears on 2+ pages, it moves to `base.css`.
- `mock-data.js` loads seed data into `localStorage` on first run (version-gated so a bump
  refreshes stale data), then all pages read/write from there — this makes cross-page flows
  (grant access in admin → viewer sees the room) feel real.

## 4. Mock Behavior Conventions

### 4.1 Session & "auth"

- Login writes a session object to `localStorage` (current user id + role).
- `mock-helpers.js` provides `requireRole('admin' | 'viewer')` which redirects to
  `../login/` when no session / wrong role. This simulates routing guards — remember it is
  cosmetic (disclaimer §2).
- Demo accounts seeded and shown on the login page as hint chips:
  - `admin@vdr.test` / `admin123` — Admin
  - `viewer@vdr.test` / `viewer123` — Viewer
  - `expired@vdr.test` / `viewer123` — Viewer with an expired grant (demo AC-6)

### 4.2 Simulated security behaviors

| Real behavior (PRD) | Mock simulation |
|---|---|
| Authorization chain per request (§9.2) | Role guard + data filtering by grants in `mock-data.js` |
| Download disabled → 403 server-side (FR-DL-2) | Button hidden **and** a `simulateApiCall()` helper that shows an "Access denied (403 simulated)" toast if triggered anyway |
| Dynamic watermark (FR-WM-*) | Real overlay implementation: tiled CSS/JS watermark over the rendered pages with name/email + timestamp + room name per effective settings |
| Access expiry / revoke (FR-ACC-4/5) | Grant records carry `expires_at` / `revoked_at`; viewer pages check them and hide/deny accordingly |
| Activity log (FR-LOG-*) | `logEvent(type, detail)` appends to the events store; admin activity/audit pages render it |
| Short-lived content tokens (NFR-SEC-2) | Not simulated — out of mock scope |

The watermark overlay should be built **properly** in the mock (it carries over to production
intent), while auth/permission logic is knowingly fake.

### 4.3 States every page must show

- **Loading** — can be brief/fake (`setTimeout`) but must exist where data "loads".
- **Empty** — e.g., viewer with no assigned rooms, folder with no documents.
- **Error/handled failure** — e.g., expired-access page, simulated 403.
- **Processing** — upload and office-conversion placeholders (skeleton/spinner states).

### 4.4 Navigation

- Cross-page links are relative and **always target the page file explicitly**
  (`../rooms/index.html`, `../viewer/index.html#doc=d-aurora-nda`). Never link to a
  directory (`../rooms/`) — `file://` has no directory-index resolution, so directory
  URLs dead-end when the mock is opened without a server. Page parameters travel in the
  **URL fragment** (`#room=…&folder=…`), not a query string — Safari drops query strings
  from `file://` URLs, while fragments survive in every browser. `VDR.utils.qs()` reads
  the fragment (with a query-string fallback).
- Viewer pages never show admin nav; admin pages never show viewer nav. One shared top-nav
- pattern per role, defined once in `base.css` + `mock-helpers.js` (render function).

## 5. Page Inventory

Build order follows BACKLOG priorities (P0 screens first). **Every seed document ships with
a real generated file** in `mock/viewer/assets/` (2 PDFs, 1 XLSX, 1 DOCX — generated
artifacts, not handwritten). In-app viewing is **plugin-free**: every document renders from
seeded `doc.preview` data in `mock-data.js` (document pages, or a spreadsheet grid for
XLSX) — identical behavior in every browser, including setups where embedded PDF plugins
are blocked. For PDFs, "Open in new tab" additionally serves the real file at full
fidelity. Real file parsing (pdf.js, SheetJS, …) is out of scope — the mock uses no CDN
libraries. The viewer's fallback state prints a one-line self-diagnosis (doc id, type,
file/preview presence, data version) and self-repairs stale demo data by reseeding once.

## 6. Mock Acceptance Checklist

A page is done when:

- [ ] Opens via `file://` with no console errors
- [ ] Uses only `base.css` + its own `style.css`; no duplicated cross-page rules
- [ ] Reads/writes state through `mock-helpers.js` + `localStorage` (no per-page data islands)
- [ ] Shows loading / empty / error states as applicable (§4.3)
- [ ] Cross-page flows work: login → rooms → room → viewer; admin changes are visible to viewer after re-navigation
- [ ] Watermark (viewer page) reflects current session user + live timestamp, tiled across the view
- [ ] Download-disabled simulation includes the fake-403 path, not just a hidden button
- [ ] Responsive enough for tablet width; desktop-first
- [ ] Logged events appear on `admin-audit/`

---

## 7. Out of Scope for the Mock

- Any real backend, API, auth, or storage
- Real file uploads (simulate with placeholder entries + processing state)
- Real office file parsing/conversion (office previews are simulated from seeded `doc.preview` data)
- MFA challenge page (P2)
- Print/export of any kind
- Cross-browser perfection — target evergreen Chrome/Safari; note issues, don't chase them

---

## 8. When Mock Phase Ends

The mock is a design artifact. Production development restarts from `PRD.md` + `BACKLOG.md`
(BACKLOG Iteration 1 onward) with a real stack decision — mock JS is **not** migrated; only
the visual language (tokens in `base.css`) and the watermark overlay approach carry over.
